# Component Conventions

How components are organized, named, split across the server/client boundary, and styled in this ERP frontend. This doc pairs with `claude.md` (the full engineering guide) and is the source of truth whenever you create or move a component.

## Folder layout

```
src/components/
├── ui/                     # shadcn primitives (Button, Card, Dialog, …) — generated by the shadcn CLI
├── Navbar/                 # index.tsx + helpers (Logo, SearchBar, UserIconButton, …)
└── Footer/                 # index.tsx + helpers (FooterLinkColumn, QuickLinks, …)
```

Two rules govern this tree:

1. **`components/ui/` is shadcn-only and flat.** That's where the shadcn CLI emits primitives, and we don't fight the CLI. Don't add hand-rolled components here.
2. **Everything else is folder-per-component.** Each public component gets a PascalCase folder named after itself with `index.tsx` as the entry. Consumers import the bare path: `import { Navbar } from '@/components/Navbar'`.

## Naming

| Thing | Convention | Example |
| --- | --- | --- |
| Component folder | PascalCase | `components/Navbar/` |
| Component entry file | `index.tsx` | `components/Navbar/index.tsx` |
| Helper component file | PascalCase | `components/Navbar/SearchBar.tsx` |
| shadcn primitive file | kebab-case (CLI default) | `components/ui/button.tsx` |
| Component identifier | PascalCase | `const Navbar: React.FC = …` |
| Hook identifier | `use` + camelCase | `useDebouncedValue` |
| Props interface | `<Name>Props` | `interface NavbarProps` |

## Helper components

Helpers that are only used by one feature live as siblings of that feature's `index.tsx`:

```
components/Navbar/
├── index.tsx
├── Logo.tsx
├── SearchBar.tsx
└── UserIconButton.tsx
```

The moment a helper is reused by a second feature, lift it to its own folder under `components/`. Don't reach across feature folders to import a sibling's helper — that's a signal to lift it.

Avoid the atoms/molecules/organisms split. Folder-by-feature scales better and keeps related code together.

## Server vs Client

- **Server Components are the default.** They render on the server, ship no JS, and can fetch data directly. Most pages, layouts, and presentational components should stay on the server.
- Add `'use client'` only when the component needs one of: hooks (`useState`, `useEffect`, Zustand), browser APIs, event handlers, or context (e.g. a `ThemeProvider`).
- **Keep the client boundary as low in the tree as possible.** A typical page is a Server Component that imports a small Client Component for the interactive part. Don't tag a whole page or layout as `'use client'` just because one descendant needs state.
- Props that cross the server→client boundary must be plain serializable values. No functions, no class instances, no Dates-as-objects-with-methods.

```tsx
// app/dashboard/page.tsx  — Server Component (default)
import { DashboardHeader } from '@/components/DashboardHeader'   // server
import { DashboardFilters } from '@/components/DashboardFilters' // client

export default async function DashboardPage() {
  const data = await fetch('…', { next: { revalidate: 60 } }).then(r => r.json())
  return (
    <>
      <DashboardHeader title="Overview" />
      <DashboardFilters initial={data.filters} />
    </>
  )
}
```

```tsx
// components/DashboardFilters/index.tsx
'use client'

import { useState } from 'react'
import { Button } from '@/components/ui/button'

interface DashboardFiltersProps {
  readonly initial: readonly string[]
}

export const DashboardFilters: React.FC<DashboardFiltersProps> = ({ initial }) => {
  const [active, setActive] = useState<readonly string[]>(initial)
  // …
  return <Button variant="outline" onClick={() => setActive([])}>Reset</Button>
}
```

## Styling

- **shadcn first.** If shadcn ships a primitive for it (Button, Card, Tabs, Dialog, Sheet, …) use it. Don't hand-roll equivalents.
- **Tokens, not literals.** Use semantic classes — `bg-background`, `text-foreground`, `border-border`, `text-primary`, `bg-card` — so the neon-on-black palette flows everywhere automatically. Never hardcode `#00ffd5`, `bg-black`, or `style={{ color: '#fff' }}`.
- **`cn()` for conditional classes.** Compose with the helper from `lib/utils.ts`; never string-concatenate class names.
- **Variants via `cva`.** When a component needs visual variants, use `class-variance-authority` the way shadcn does — don't invent a parallel system.
- **No inline `style={{ … }}`** for anything tokens can express. Inline styles are reserved for dynamic values that genuinely can't be a class (e.g., a computed grid template).

```tsx
// Good
import { cn } from '@/lib/utils'
import { Button } from '@/components/ui/button'

<Button
  variant="default"
  className={cn('w-full', isActive && 'ring-2 ring-ring')}
>
  Save
</Button>

// Avoid
<button
  style={{ background: '#00ffd5', color: '#000', padding: 12 }}
  className={`w-full ${isActive ? 'ring-magenta' : ''}`}
>
  Save
</button>
```

## Props contracts

- Props interfaces are named `<Name>Props` and live in the same file as the component (or `types.ts` if the component is large enough to warrant splitting).
- Mark props `readonly`. Mark arrays `readonly T[]`.
- Use discriminated unions for components that genuinely have variants in *shape*, not just style. Style variants belong in `cva`.

```tsx
interface NavbarProps {
  readonly user: User | null
  readonly cartCount: number
  readonly onLogout: () => void
}
```

## Tests live next to components

```
components/Navbar/
├── index.tsx
├── Logo.tsx
├── SearchBar.tsx
└── Navbar.test.tsx
```

Test the rendered output, not implementation details. Use `getByRole`, `getByText`, `getByLabelText` over `getByTestId` where possible. See `claude.md` for full testing guidance.

## Quick checklist before merging a new component

- [ ] Folder is PascalCase, entry is `index.tsx`
- [ ] Helpers colocated; nothing imported across unrelated feature folders
- [ ] `'use client'` only if the component actually needs it
- [ ] No hardcoded colors; only semantic tokens
- [ ] Uses shadcn primitives where one exists
- [ ] Props interface is `readonly`, named `<Name>Props`
- [ ] Test file sits next to the component and asserts user-visible behavior
